# Security Policy

The security of **Re-Editor** and its users is taken very seriously. We appreciate responsible disclosure of security vulnerabilities and make every effort to address valid concerns promptly.

---

## Supported Versions

Security updates and critical patches are actively provided for the following versions:

| Version | Supported          |
| ------- | ------------------ |
| `dev` (main branch) | :white_check_mark: |
| `v2026.0.x` | :white_check_mark: |
| `< v2026.0.0` | :x:                |

---

## Reporting a Vulnerability

If you discover a potential security vulnerability in Re-Editor, please do **NOT** open a public issue or discuss it publicly. Instead, follow these steps:

1. **Email Disclosure**:
   Send an email to [mpetrivlin@gmail.com](mailto:mpetrivlin@gmail.com) with the subject line:
   `[SECURITY] Re-Editor Vulnerability Report`

2. **GitHub Private Advisory**:
   Alternatively, submit a report via [GitHub Private Vulnerability Reporting](https://github.com/fapethedev/re-editor-for-coding/security/advisories/new) if enabled on the repository.

### What to Include in Your Report
To help us investigate and remediate the issue quickly, please provide:
- A clear description of the vulnerability and its potential impact.
- Step-by-step instructions or a minimal Proof of Concept (PoC) to reproduce the issue.
- Relevant component or file paths affected.
- Any suggested mitigations or patches, if available.

---

## Response Process & Timeline

- **Acknowledgment**: We aim to acknowledge receipt of your vulnerability report within **48 hours**.
- **Investigation**: We will assess the validity and severity of the report and provide an estimated timeline for remediation.
- **Fix & Deployment**: Once validated, a fix will be developed, tested, and released.
- **Public Disclosure**: We will coordinate with the reporter to agree on a public disclosure date once the fix has been published.

---

## Security Best Practices for Web Editors

When working with web text and code editors in this repository, follow these guidelines:

- **HTML Sanitization**: Any raw HTML generated by rich text editors (such as Quill.js) must be treated as untrusted and safely sanitized before rendering in user contexts to prevent Cross-Site Scripting (XSS).
- **Dependency Auditing**: Regularly run automated security audits using `pnpm audit` to detect known vulnerabilities in third-party dependencies.
- **Client Sandbox Isolation**: Ensure code execution environments (e.g. Monaco code snippets) operate with appropriate browser-level isolation.
